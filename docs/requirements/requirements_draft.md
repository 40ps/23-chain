### Turing Machine

- [PROMPT] The Wolfram (2,3) machine has two states, three symbols, and six transition rules.
- [CODE] `core/turing.ts` implements the six Wolfram (2,3) rules from the prompt.
- [README] The README documents the same six transition rules.
- [PROMPT] Each step must read the current symbol, look up the transition, write the new symbol, update state, move the head, encode full state, and create a simulated or real transaction.
- [CODE] `useTuringMachine.ts` performs that sequence for simulation and record-only live-step construction.
- [PROMPT] Step execution must be sequential and deterministic.
- [PROMPT] Multiple steps must not run in parallel.
- [PROMPT] The execution loop must be async and must await between steps.
- [PROMPT] Double execution must be prevented if the user clicks multiple times.
- [CODE] `useTuringMachine.ts` uses refs and guards for running state, abort state, async loop state, and pending live steps.

### Tape

- [PROMPT] The tape must behave as infinite in both directions.
- [PROMPT] The tape must auto-expand left and right.
- [PROMPT] The default value outside initialized cells must be `0`.
- [PROMPT] The head must never be out of bounds.
- [PROMPT] If the head moves left beyond index `0`, the tape must prepend `0` and keep the head at position `0`.
- [PROMPT] If the head moves right beyond tape length, the tape must append `0`.
- [PROMPT] The tape must support large inputs of several thousand characters.
- [CODE] `core/tape.ts` implements a dynamic tape with `cells` and `offset`.
- [CODE] `readCell` returns `0` outside the stored range.
- [CODE] `writeCell` expands left and right.
- [CODE] `moveHead` prepends on left underflow and appends on right expansion.
- [CODE] `validateTapeString` rejects empty input and symbols other than `0`, `1`, and `2`.
- [CODE] `parseTapeString` silently drops invalid characters if used without validation.

### State Encoding

- [PROMPT] Each step must encode the full machine state.
- [PROMPT] State encoding must concatenate state, separator, head position, separator, and tape.
- [PROMPT] Tape must be encoded as a base-3 string containing only `0`, `1`, and `2`.
- [PROMPT] JSON must not be used for tape encoding.
- [PROMPT] The canonical example is `1|42|000120201`.
- [PROMPT] The encoded state must be converted to hex before OP_RETURN use.
- [PROMPT] Encoding must be deterministic and minimal.
- [CODE] `encodeState` returns the separator-delimited state string.
- [CODE] `encodeStateToHex` converts the separator-delimited state string to UTF-8 hex.
- [CODE] `decodeStateFromHex` decodes hex back into state, head position, and tape values.
- [CODE] `decodeStateFromHex` does not fully validate decoded state range, head position semantics, or tape symbols.

### Simulation Mode

- [PROMPT] Simulation Mode is the default mode.
- [PROMPT] Simulation Mode must be fully functional offline.
- [PROMPT] Simulation Mode must not broadcast real transactions.
- [PROMPT] Simulated TXIDs must be deterministic.
- [PROMPT] Simulated TXIDs must use `SHA256(encodedState)`.
- [PROMPT] The same state must always produce the same simulated TXID.
- [PROMPT] Random values must not be used for simulated TXIDs.
- [CODE] `txSimulator.ts` computes simulated TXIDs with Web Crypto SHA-256 over the encoded state string.
- [CODE] `simulateTransaction` records encoded state, hex encoded state, OP_RETURN data, timestamp, mode, payload size, and transition description.
- [README] The README documents `TXID = SHA256(encodedState)`.

## Protocol Evolution Stages

- [README] Stage 1 is Simulation Mode, where computation is pure in-browser execution and simulated TXIDs are hashes of encoded states.
- [README] Stage 2 is Record-Only Live Mode, where real BSV transactions record state in OP_RETURN but do not enforce transition validity on-chain.
- [README] Stage 3 is Genesis Covenant Mode, where OP_PUSH_TX-style transaction-preimage techniques and Genesis-restored opcodes are intended to validate transitions on-chain.
- [README] Stage 4 is Chronicle OTDA Mode, where `SIGHASH_OTDA = 0x20` is intended to provide a cleaner covenant construction.
- [CODE] `scriptModes.ts` models Record-Only as active, Genesis Covenant as template, and Chronicle OTDA as todo.
- [CODE] `docs/script-design.md` also describes a state hash commitment level between logging and full covenant enforcement.
- [INFERENCE] The protocol evolution is both a roadmap and an explanatory framework for comparing computation logging with computation enforcement.
